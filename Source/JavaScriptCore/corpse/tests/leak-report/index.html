What counts as finding a leak

A person who suspects a leak takes two heap snapshots and reads what grew between them. To fix the leak, they need what holds it: the JS object the page's code keeps adding to. The test records that holder by its address, which holds nothing. A walk finds the leak only if both of these hold.

It charges the leak to the holderEvery leaked object is a node. The holder is on a path from <root> to each one, and its retained size grew by at least half of what leaked.
The holder's entry stands outNodes are grouped by retained path, the classes on their path of dominators from <root>. The holder's entry must be charged with at least half of the leak and with nothing of the other demo's. No unrelated entry may grow more by noise, meaning growth no leak owns.

These belong to no entry: the allocator's own blocks, nodes that no path reaches, and the JS heap's record of each block (its MarkedBlock::Handle and whatever that alone holds, such as the WeakBlocks of its weak set). All of these grow with whatever the heap holds.

Each demo

The script is run as written. The holder line is the test's addition: it records addresses only and holds nothing. Below each script is the list of what grew most, then the dominator tree of the whole heap, in which a parent retains everything beneath it. Each node's children are sorted by growth, so the subtrees that grew most come first, and each row shows how much of each demo's leak lies below it. Open a node's edges to see every labeled edge into and out of it. mya labels each edge with the C++ member or class that held it. JSC's snapshot supplies JS property and variable names. JSC's snapshot has no C++ objects: it records an edge for a cell only while another cell's visitChildren marks it. A removed element's C++ children, and their pointers to their wrappers, are no edges, so in JSC's snapshot each child's wrapper is a root of its own.
